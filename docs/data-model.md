# Datamodell

All tables live in the Postgres schema **`zenith_fit`** in the shared Supabase
project `isaly-apps-prod` (the same project `happy-hen-history`,
`plant-care-assistant`, `calorie_tracker`, `instant-job-insight` and
`study-buddy-planner` use). The schema is chosen instead of `public` for the
same reason as `plant-care-assistant`: it keeps Zenith Fit AI fully isolated
from other Isaly apps' tables (e.g. `public.profiles` and
`public.notifications` already exist for another app), and it makes RLS
policies easy to reason about per app.

Source: [`supabase/migrations/20260821120000_zenith_fit_schema_init.sql`](../supabase/migrations/20260821120000_zenith_fit_schema_init.sql).

## Tables

### `profiles`

One row per user (`id` = `auth.users.id`). RLS: a user can only read/write
their own row.

| Column             | Type   | Description                                                                                                      |
| ------------------ | ------ | ---------------------------------------------------------------------------------------------------------------- |
| `name`             | text   | Display name shown in the dashboard greeting                                                                     |
| `limitations`      | text[] | Body areas the AI physiotherapist screens for (`knees`, `back`, `shoulders`, `neck`, `hips`, `wrists`, `ankles`) |
| `limitation_notes` | text   | Free-text detail, e.g. "left knee meniscus"                                                                      |
| `preferred_types`  | text[] | Preferred `WorkoutTypeId`s, used to seed the weekly plan and new-session defaults                                |
| `weekly_target`    | int    | Sessions per week (1–7); rest days are spread evenly around it                                                   |

### `workouts`

One row per generated session. `id` is client-generated by the rule-based
engine (`src/lib/fitness/engine.ts`), so it's a `text` primary key rather
than a database-assigned `uuid`. RLS: a user can only read/write their own
rows.

| Column           | Type          | Description                                                                     |
| ---------------- | ------------- | ------------------------------------------------------------------------------- |
| `scheduled_for`  | timestamptz   | When the session was generated/planned for                                      |
| `time_of_day`    | text          | `morning` \| `lunch` \| `afternoon` \| `evening`                                |
| `type` / `types` | text / text[] | Primary + all selected `WorkoutTypeId`s                                         |
| `duration`       | int           | Minutes                                                                         |
| `intensity`      | text          | `restorative` \| `easy` \| `moderate` \| `hard`                                 |
| `coach_note`     | text          | Generated coaching note for this session                                        |
| `physio_note`    | text?         | Present when exercises were swapped for a limitation                            |
| `blocks`         | jsonb         | `WorkoutBlock[]` — warm-up/main/cool-down exercises with cues and minutes       |
| `completed_at`   | timestamptz?  | Set when the user finishes the session                                          |
| `feedback`       | jsonb?        | `{ difficulty, energy, soreness, mood, note }` — feeds the next readiness score |

### `goals`

User-defined session/minute/streak targets.

| Column   | Type | Description                         |
| -------- | ---- | ----------------------------------- |
| `metric` | text | `sessions` \| `minutes` \| `streak` |
| `target` | int  | Target value                        |
| `period` | text | `week` \| `month`                   |

## Notes

- `blocks` and `feedback` are stored as `jsonb` rather than normalized tables
  — they're always read/written as a whole per session and never queried by
  their internal fields, so normalizing would add joins with no benefit.
- The client (`src/integrations/supabase/client.ts`) is configured with
  `db: { schema: "zenith_fit" }`, so app code calls `supabase.from("workouts")`
  etc. without repeating the schema name.
